# مصفوفة قراءة API وSupabase — 0.9.0

ربط GitHub يتيح تحليل المصدر. اختبار عزل المستخدمين يحتاج أصل API وحسابين وموردين تجريبيين. أضيف لهذا الغرض محرك فعلي اختياري داخل التحليل العميق، وليس تحويل البنود غير المنفذة إلى نجاح.

## الإعداد

1. افتح ربط GitHub، ثم «API وSupabase — مصفوفة عزل القراءة» أسفل مشروعك.
2. جهز بيئة اختبار تملكها، وحسابين منخفضَي الصلاحية A وB. استخدم access token الحالي لكل حساب، لا كلمة المرور ولا service_role ولا مفتاح إدارة. حسابان مختلفان فعلًا؛ التوكنان المختلفان لنفس مستخدم JWT مرفوضان.
3. جهز موردًا يملكه A وآخر يملكه B. ضع `aegis-test-owner-a` كقيمة نصية كاملة في حقل مورد A، و`aegis-test-owner-b` في مورد B؛ يمكن تخصيص العلامتين. لا تستخدم سجلات عملاء أو موارد إنتاج.
4. أدخل أصل API، مثل `https://your-project.supabase.co`، بلا مسار. لا يشترط مطابقته لنطاق الموقع. اختر API أو Supabase REST أو Storage. في Supabase أدخل مفتاح publishable أو anon العام؛ المفاتيح ذات الصلاحية المرتفعة مرفوضة.
5. أدخل مسار GET لكل مورد. مثال REST: `/rest/v1/aegis_fixtures?select=marker&id=eq.UUID_A&limit=1`، وللمورد الآخر UUID_B. يجب أن تكون الاستجابة JSON تحتوي العلامة كقيمة نصية. Storage: مسار ملف نصي خاص يحتوي العلامة فقط؛ لا تستخدم مسار public لمورد يفترض عزله.
6. احفظ الإعداد. كل التوكنات وعلامات الموارد والمسارات تحفظ مشفرة باستخدام مفتاح الخادم؛ لا تعاد التوكنات إلى المتصفح بعد الحفظ.
7. انشر رمز إثبات المشروع المعروض في ملف نصي على أصل API نفسه، بالمسار الذي أدخلته. Supabase يسمح بملف في bucket عام مخصص للتحقق: `/storage/v1/object/public/aegis-verification/aegis-audit.txt`. هذا الملف للإثبات فقط؛ موارد اختبار العزل تبقى خاصة. اضغط «تحقق من أصل API». لا يتبع التحقق إعادة توجيه، ولا يرسل التوكنات.
8. ابدأ تحليلًا عميقًا جديدًا وفعل «اختبار عزل قراءة API وSupabase». لا يشترط فحص HTTP للموقع لتفعيل API إذا كان أصل API موثقًا مستقلًا. OSV خيار منفصل.

التحقق صالح سبعة أيام. تغيير الإعداد يبطله؛ يجب إلغاء الفحص النشط قبل استبداله. حذف الإعداد يلغي فحص API الجاري. التوكنات المنتهية تتطلب تحديث الإعداد والتحقق ثم إعادة الفحص. احتفظ بمجلد data ومفتاح `.repository-key` أو REPOSITORY_ENCRYPTION_KEY عند الترقية.

## ماذا ينفذ؟

ست حالات قراءة مخططة: A يقرأ مورده، B يقرأ مورده، B يحاول قراءة مورد A، الزائر يحاول مورد A، A يحاول مورد B، الزائر يحاول مورد B. يثبت وصول المالكين أولًا. إذا فشل baseline، لا يحتسب رفض الحساب غير الصالح نجاحًا للعزل.

- نجاح وصول المالك: HTTP 200 مع العلامة الصحيحة.
- كشف مثبت: استجابة ناجحة لغير المالك تعيد علامة المورد. تنشأ ملاحظة عالية الخطورة لهذا المورد.
- منع قراءة: HTTP 401/403/404 بلا العلامة، أو HTTP 200 مع مصفوفة JSON فارغة في API/REST فقط، بعد ثبوت baseline اللازم.
- غير حاسم: تحويل، انتهاء توثيق، تعذر اتصال، JSON غير متوقع، عدم ظهور العلامة في baseline. تظهر الحالة والسبب ولا تدخل كنجاح.

طلبات GET فقط، أصل ثابت مثبت عبر DNS العام، بلا تحويلات أو شبكات خاصة، وبحد استجابة 64KiB ومهلة 10 ثوانٍ للطلب. الإلغاء يوقف الطلب الجاري. لا تخزن أجسام الاستجابة أو التوكنات في التقرير. يظهر المورد والهوية والطريقة والوقت وحالة HTTP والحجم والزمن والمتوقع والمرصود. يحتفظ السجل بكل الحالات الست حتى التي لم ترسل.

## الشفافية والحدود

من سجل الفحوص يمكن البحث في القواعد والملفات والأدلة وتنزيل JSON للنتائج في المحور/المجموعة المعروضة، دون أن تقلصه تبويبات الحالة أو البحث. تبويب كل الفحوص مع كل المحاور يصدّر جميع النتائج. التقرير Markdown يتضمن تفاصيل التنفيذ أيضًا.

نجاح هذه المصفوفة يثبت سلوك قراءة الموردين للطلبات الست فقط. لا يثبت حالة RLS الفعلية في قاعدة البيانات أو كل الجداول، ولا يختبر INSERT/UPDATE/DELETE أو رفع ملفات أو كل CSRF/XSS/SQLi أو business logic. هذه القيود تظل واضحة؛ لا توجد أداة تضمن حصر كل الثغرات بمجرد ربط مستودع أو إدخال رابط. البنود الأوسع في سجل HTTP لا تُستبدل بنتيجة نجاح الموردين.

لا تختبر هذه النسخة تسجيل الدخول بكلمات مرور أو تجدد توكنات الحسابات. المستخدم يجهز حسابات اختبار وعلامات موارد محددة. Ollama يستقبل نصوص النتائج فقط؛ لا تصله صور أو توكنات الإعداد.
